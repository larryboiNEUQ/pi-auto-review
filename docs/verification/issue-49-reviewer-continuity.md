# Issue #49 — bounded reviewer context continuity

Draft PR #52, dedicated issue worktree `feat/issue-49-reviewer-continuity`. This is a reviewer-request/context change, **not** a grant cache, Pi session rule or a provider prompt-cache claim.

> **Superseded in part (2026-09-29, `bounded-provenance-v2`, #57 / ADR 0010):** the `edited_context_history` and post-compaction fail-closed admissions described below were replaced by marked in-band omissions — review proceeds and grants must come from retained host-user evidence. Branch-identity invalidation and `authorization_changed` still apply unchanged.

## Contract

- Chat first sends the existing full, admitted dossier. A subsequent request can use an explicitly assembled, bounded evidence-prefix plus evidence-delta and **only the pending exact action** when the host session, active branch-entry prefix, reviewer identity, effective config and mandatory user/system authorization match. Previous actions, model outputs and manual approvals are not carried forward as authorization. A missing/invalid branch cursor, incompatible evidence prefix, changed restrictions or an oversized delta resets to the full admitted dossier. Both full and delta requests include the current action and are measured against the reviewer window; mandatory-history loss fails closed.
- Jev receives its ordinary fully assembled bounded state and questions on each request. Chat/evaluation see equivalent decision-relevant current evidence; the adapters do not claim network-side prompt caching or shared model memory.
- Each extension instance owns bounded, temporary cursors. Start/shutdown clears them; reload/resume reconstructs a bounded snapshot from the host active branch (not persisted raw transcript), and a fork uses only that branch's legitimate entries. Session model selection storage remains separate and unchanged.
- An in-flight review is valid only if the owner, authorizing branch identity, effective config and admitted evidence/diagnostics match again before release. Authorizing branch identity is the active `getBranch()` id sequence excluding host bookkeeping (`session_info`, `custom`, `label`, `model_change`, `thinking_level_change`). A new message, compaction, context edit, or unrecognized entry still changes that identity. Pending user input is checked using Pi's public `hasPendingMessages()` because steering may not yet be in SessionManager. A late result from a revoked grant is denied and audited `authorization_changed`. The permission-system authorizer selection uses the same identity after the **entire** reviewer/terminal chain and before approving or recording a session rule. Concurrent direct asks have isolated contexts and a late commit cannot overwrite a newer cursor; cancellation/deadline and ordinary terminal fallback remain compatible.
- The audit records continuity mode and reset reason, never the retained context. Provider/model/policy remain auditable via existing fields. No live inference or browser execution is claimed from scripted adapters.
- Pi's parallel dispatcher prepares all calls before invoking any executor. No public pre-executor authorization hook can revalidate an earlier prepared approval while a sibling later waits. Guardian requires affirmative single-call proof from the active host assistant message. Multiple calls, missing tool-call IDs, and unmatched messages fail closed before inference/terminal escalation; missing proof is **not** treated as single-call safety. Forwarded child asks omit the toolCallId and the parent transcript cannot attest the child's batch: parent Guardian therefore denies forwarded asks until trusted originating proof becomes available. Child lineage and forwarding infrastructure are separately tracked in Issue #37, **not** the bounded-investigation Issue #50; this work does not claim that #37 already supplies that proof. A real two-call Agent dispatcher test holds a sibling, queues revocation and asserts neither executor runs; a forwarded-request-server integration test verifies the parent denial. This intentionally sacrifices batched and forwarded delegated asks; ordinary verified single-call terminal fallback remains supported. **Superseded for forwarded asks after #37 merged:** the child now attests its own batch on the forwarded request (`batchProvenance`), and the parent reviews a single-call attestation normally; missing, unknown or multi-call attestations still fail closed.
- A branch-local `context_edit` may change an older user grant only in newer Pi's projected context (global 0.87.1), while raw `buildContextEntries()` still contains the old text. Until a provenance-preserving projection is available to the pinned 0.81 integration, any such edit in the active evidence fails admission closed (`edited_context_history`).
